## Назначение основных каталогов и файлов

Основная структура проекта:

```text
Dockerfile
docker-compose.yml
requirements.txt
pytest.ini
TEST_DOCUMENTATION.md
tests/
```

Назначение основных каталогов и файлов:

- `Dockerfile` — описывает контейнер `tests`, внутри которого устанавливаются Python-зависимости и запускается pytest;
- `docker-compose.yml` — описывает три контейнера: Selenium Hub, Chrome node и контейнер с тестами;
- `requirements.txt` — содержит библиотеки, необходимые для запуска автотестов;
- `pytest.ini` — хранит настройки pytest и зарегистрированные маркеры тестов;
- `TEST_DOCUMENTATION.md` — описание реализованных тестов 4 итерации;
- `tests/` — каталог с автотестами, фикстурами и Page Object классом;
- `tests/e2e/` — тестовые сценарии, каждый файл соответствует отдельному тест-кейсу;
- `tests/pages/` — вспомогательные классы для работы со страницей Learn Git Branching.

### Page Object классы

В проекте используется Page Object подход. Общая логика работы с сайтом вынесена в файл:

```text
tests/pages/learn_git_branching_page.py
```

Класс `LearnGitBranchingPage` отвечает за повторяющиеся действия на сайте:

- открытие нужного уровня;
- пропуск стартовых и уровневых инструкций;
- выбор уровня через интерфейс;
- ввод команд в консоль тренажёра;
- обработку интерактивного rebase через модальное окно сайта;
- ожидание завершения анимаций и команд;
- проверку успешного прохождения уровня;
- получение текста графа коммитов для проверок.

Благодаря этому сами тесты в `tests/e2e/` остаются короткими: в них описан сценарий конкретного тест-кейса, а техническая работа с интерфейсом находится в Page Object.

### Фикстуры pytest

Фикстуры расположены в файле:

```text
tests/conftest.py
```

Основные фикстуры:

- `selenium_url` — получает адрес Selenium Grid из переменной окружения `SELENIUM_REMOTE_URL`;
- `driver` — создаёт Selenium Remote WebDriver, подключённый к Chrome node в Docker;
- `lgb` — создаёт объект `LearnGitBranchingPage`, через который тесты работают с сайтом.

Перед созданием браузера выполняется ожидание готовности Selenium Grid. Это нужно, чтобы тесты не стартовали раньше, чем контейнеры `selenium/hub` и `selenium/node-chrome` будут готовы принимать команды.

## Объединение наработок

В дополнительной части 4 итерации была выполнена интеграция наработок второго участника в текущую конфигурацию проекта. Основной идеей было сохранить централизованный запуск тестов через Docker, Selenium Grid и pytest, но расширить общий интерфейс работы со страницей.

Из структуры второго участника были перенесены полезные идеи:

- проверка вывода терминала после выполнения команд;
- методы для определения ошибок в консоли;
- методы для проверки подсказок;
- проверка окна цели уровня;
- сценарии для уровней 13-16.

При этом тесты были адаптированы под общую конфигурацию проекта:

- запуск выполняется через `docker-compose.yml` с контейнерами `selenium/hub`, `selenium/node-chrome` и `tests`;
- все тесты используют единый fixture `lgb`;
- все действия с сайтом выполняются через общий Page Object `LearnGitBranchingPage`;
- сохранён единый формат имён файлов `test_tc_XX_p/n...py`;
- тесты задач 9-16 запускаются одним набором из папки `tests/e2e/`.

### Преимущества объединения

- Тесты запускаются централизованно одной командой без ручной настройки ChromeDriver.
- Все уровни используют одинаковые ожидания загрузки сайта, анимаций и выполнения команд.
- Повторяющиеся действия вынесены в один Page Object, поэтому тестовые файлы остаются короткими и читаемыми.
- Методы проверки терминала, ошибок, подсказок и окна цели доступны всем тестам через общий интерфейс.
- Новые тесты можно добавлять быстрее: достаточно указать уровень, команды и ожидаемый результат.
- Docker-окружение стало единым для всех тестов, поэтому результат легче воспроизвести на другом компьютере.

## Структура тестов


В названии файла используется:

- `p` — позитивный сценарий;

- `p1`, `p2` — два позитивных сценария;
- `n1`, `n2` — два негативных сценария.
